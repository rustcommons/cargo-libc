# cargo-libc 0.1.1

Provider-backed shared libraries and Python extensions can link without executable startup objects.

Original crates.io publication: 2026-10-13 (UTC). Package `cargo-libc` 0.1.1
is available and non-yanked, checked 2026-11-02. Source tag `v0.1.1`:
`b9d2c4f17848d8b0bba56178d5ee6090b1feffd6`.
These notes were reconstructed on 2026-11-02; their later GitHub publication date
is documentation backfill, not the original software release date. They were not
present at the historical tag and do not modify its package.

## Changes

- Detect shared links and omit executable `crt1.o`; use the shared GCC startup
  objects for `cdylib`/shared outputs.
- Stop forcing static Rust relocation in provider mode, allowing position-independent
  extension code while keeping managed executables non-PIE.
- Document `cargo libc env` with maturin/PyO3 and add a maintained Python example.

## Upgrade

Install `cargo-libc` 0.1.1 with `--locked`, keeping its five executables together.
Provider descriptors and dependency versions remain unchanged from 0.1.0.
Regenerate machine-specific Cargo configuration before building an extension;
inspect its GLIBC requirements separately. This does not supply a Python/C++
runtime or qualify every wheel/host/interpreter combination.

## Validation and limits

The contemporaneous record reports CI 13/13 and a registry-installed build of
the example's glibc 2.17 wheel. It also records bounded PyO3/maturin and matching
userland checks; those outcomes remain attributed to that record. This backfill
verified archive/tag equality, not a fresh rerun or recovery of every original
artifact. Shared-library support is not a universal cross-DSO unwind guarantee;
real old-kernel/system qualification remains a separate gap.
