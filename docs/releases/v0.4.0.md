# cargo-libc 0.4.0 candidate

Prepared 2026-11-03; **not published or release-qualified**. This minor candidate
contains merged capability diagnostics and current-runtime documentation, including
a deliberate local missing-interpreter refusal/exit-status change. Package and clean
unpacked locked-install qualification, final release review/merge, publication,
immutable tag, official archive, docs.rs, published installation and GitHub Release
remain pending. No publication or tag is authorized by this preparation.

## Changes

- Doctor/build diagnostics distinguish tool build ABI provenance, bounded mapped-libc
  observations, selected glibc provider/sysroot inputs and selected execution route.
  Static tools, conflicting evidence and inconclusive observations remain unknown;
  no distro-name or compile-time-ABI installation/build rejection is introduced.
- Local execution checks validated ELF PT_INTERP availability before launch. A
  confirmed missing absolute interpreter refuses with status 2; inconclusive
  lookup warns and attempts execution. Container execution skips the local-loader
  check. A present loader is not a runtime-compatibility certificate.
- Current-runtime guidance explains deployment glibc and matching-architecture
  libgcc_s.so.1 prerequisites, required symbol/version pairs and package/SONAME
  distinctions. Build tools are not required merely to deploy the application.
  Inspect reports requirements; its glibc ceiling does not validate GCC ABI or
  full runtime closure. Maintained release documentation/history is also included.

System unwinder/libgcc selection, five-clock policy, caller linker state and
host/target separation remain unchanged. There is **no LLVM runtime replacement,
classifier research or target-libgcc comparator implementation** in this candidate.
The historically named unwinder plan is deferred research with no assigned release.

## Upgrade

Under the current 0.x policy this is **0.4.0, not 0.3.1**. In published 0.3.0,
a direct run that passed existing checks and reached an OS launch failure from a
missing ELF interpreter returned helper error 1. The new preflight deliberately
refuses that run before launch with status 2. The [0.3.0 launch path](https://github.com/rustcommons/cargo-libc/blob/v0.3.0/src/simulate.rs)
and [helper error mapping](https://github.com/rustcommons/cargo-libc/blob/v0.3.0/src/bin/libc-runner.rs)
establish the old behavior; the [merged preflight](https://github.com/rustcommons/cargo-libc/blob/748ffa23274792dd21e1cb4cd812271f1f61e1a3/src/simulate.rs)
establishes the new refusal. Existing glibc refusals could already return 2; this is not a claim that every old missing-interpreter path returned 1.
Scripts that distinguish helper failures from refusals must accept this change.
Successful child exit statuses, data streams and inspect contracts remain intact;
human doctor/build text gains the scoped capability information.

Dependency requirements and resolved registry checksums are unchanged. Only the
root cargo-libc package/lock entry changes from 0.3.0 to 0.4.0. Rust 1.90 and
native-tool floors are unchanged; no producer/data release is required. No new
configuration mode or runtime selection is introduced. Update all five sibling
executables together when a qualified release eventually becomes available;
installation/package validation is not claimed at this preparation stage.

## Validation and limits

Implementation was independently reviewed at exact
`d6b5f78fb31f7f6a5d8c604a313c78039573f9aa` and merged normally as
`748ffa23274792dd21e1cb4cd812271f1f61e1a3`; the merge tree equals that reviewed head.
[CI 41633902033](https://github.com/rustcommons/cargo-libc/actions/runs/41633902033)
and [PR CI 41633910012](https://github.com/rustcommons/cargo-libc/actions/runs/41633910012)
passed 15 jobs each. Together with
[push release-doc CI](https://github.com/rustcommons/cargo-libc/actions/runs/41633902688)
and [PR release-doc CI](https://github.com/rustcommons/cargo-libc/actions/runs/41633909999),
all **32 checks** passed at that exact head. This is implementation evidence at
package version 0.3.0, not 0.4.0 package/install qualification.

Named checks include corrected Windows portability (78 library tests), Linux
portable/process/MSRV/docs gates, Clang link checks, provider and container
preparation, C/CMake, Python extension imports, both plain-Cargo formats and SLES
container execution. Linux aarch64 local validation passed 82 library and nine
process tests, fmt, Clippy and warning-denied docs. Focused fixtures distinguish
mapped glibc/musl/unknown evidence, interpreter availability, local/container scope,
probe-free inspection and closed-pipe status behavior. They do not qualify a real
musl or statically linked build host. This version/docs-only preparation uses
fmt, locked metadata/graph comparison, release-doc/link/render/diff checks; it does
not rerun or extend the native runtime matrix.

Both source and container **provider preparation** require x86_64 Linux and host
GCC/binutils/startup files; container preparation also needs its selected engine
and image. Source preparation uses GCC with recorded/selected include inputs and
object verification. Container **execution** supplies its own userland/loader but
shares the host kernel; it does not install a host GNU loader. Build-only/inspect
routes do not require local target execution. Selected-mode errors remain errors,
without silent fallback.

Non-glibc/static-host combinations, complete GCC/symbol/transitive/plugin closure,
general runtime safety and actual old-system tier 3 remain unqualified. Existing
clock/unwinder interoperability limits and prebuilt-provider legal gates are unchanged.
No new platform support or broader compatibility claim is made.
