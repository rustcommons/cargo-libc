## Three different identities

1. **Static recipe/selection identity R.** Hash only known declarations: runtime policy revision, requested candidate mode, target, intended archive configuration, pinned source/inventory revision, producer implementation revision, selected provider/configuration declarations and tool selection declarations. It can be computed without opening LLVM inputs, running LLVM tools, querying resource paths or building an archive. Paths/declarations do not attest to their current contents. Do not label R an all-input fingerprint or a verified archive identity.
2. **Verified preparation identity I and archive digest A.** Producer-owned identity of the actual selected/staged headers, raw libc, provenance inputs, compiler/resource/support inputs and build configuration within its declared observation contract, plus the validated archive digest. Obtain these only when a final executable genuinely activates preparation. Keep declared compiler-closure and runtime-compatibility limits explicit. I is not a universal hermeticity or application-safety certificate.
3. **Cargo invalidation revision E.** A revision in Cargo-visible target flags, changed when a previously activated executable's recorded inputs are observed stale. E is an invalidation signal, not an archive hash. A validated executable receipt binds the actual completed output bytes (conventional SHA-256 and length), target/output kind and R, E, I and A together; a pathname is only a locator. Do not overwrite R with I after the first link: that would cause a gratuitous second build just to stabilize flags.

Existing Cargo can notice changed rustflags; hidden linker-helper environment values and cache-file changes alone are insufficient. Cargo may mark a unit fresh without running rustc or the linker. A check only inside libc-linker cannot detect a change on that path. No RUSTC_WRAPPER trick, forged compiler version, Cargo fingerprint-directory edits, touching user source or unstable build-plan feature is proposed.

## Configuration generation: no LLVM probes

Generate shell/TOML from static declarations R and an explicit configuration/invalidation revision. Preserve current provider/sysroot/clock validation; add no LLVM tool/header/resource/cache preparation probes. System mode ignores runtime receipts completely. Extension-only configuration generation has the same absence of LLVM activity, even if a previous build in the workspace produced an executable.

A missing clang++/archiver/runtime preparation cache is not a configuration-generation failure. A configuration with no verified executable receipt says exactly that: selected recipe, preparation deferred, current input/archive identity unknown. Do not fill an identity field with a pathname hash, zero digest or previously recorded digest described as current.

Saved configurations contain a snapshot of R/E. Merely reading mutable state behind a stable linker pathname or environment variable does not change Cargo's fingerprint. Configuration text must not be rewritten behind the user's back while Cargo is running.

## First final-executable activation

- Host compilation bypasses target runtime policy. Target compile/archive/rlib/shared/Python/relocatable outputs retain baseline runtime assembly and do not call LLVM preparation. Output kind comes from the reviewed completed Clang stream, not a Cargo subcommand or source filename.
- A target executable under the candidate request passes the separate supported-input/binding guards. Only then resolve the necessary runtime tools/headers and invoke a corrected producer preparation API. Missing, mismatched, unsafe or corrupt inputs fail clearly; no system fallback.
- Reuse or build the verified archive lazily, apply only a separately reviewed executable link recipe, recheck effective output kind, link and validate the resulting artifact. A visibility profile alone is not that recipe.
- Publish an executable receipt only after successful link/validation. Record the conventional SHA-256 and length of the completed output bytes, validated target/ELF kind, output locator, configuration context, R/E/I/A, actual selected-input inventory and producer provenance. Certify the final bytes after any intended stripping/postprocessing; later replacement or modification invalidates the receipt even at the same pathname. Failed preparation/link produces no successful receipt. Receipt/state paths must be normalized and contained; the rejected c7 path handling is not reused.
- Several executables can share a verified content-keyed producer archive. Each has its own artifact receipt. Mixed-workspace DSOs do not inherit executable link flags or archive linkage from an rlib, a shared environment search prefix or a global compiler option.

## Later managed commands: stale detection before Cargo freshness

Proposed managed preflight operates on receipts for previously activated executable inputs in the selected configuration namespace. It must not build LLVM or launch LLVM tools. Request a producer-owned **read-only recorded-input validation capability**: verify the receipt's bounded file/directory inventory, canonical containment, selected mappings and cached archive integrity. It must detect additions/removals, content changes at unchanged paths/mtimes and missing inputs; checking only previously opened header files is insufficient. Unknown or unobservable dependencies remain explicit limits, not an invented complete closure.

If there is no executable receipt, current identity is **unknown**, not unchanged. Do no LLVM work merely during configuration generation. An actual executable link can establish the first verified receipt; Cargo claiming that an existing artifact is fresh cannot substitute for it. If a requested executable is returned fresh without a matching verified receipt, managed completion/execution must reject it and require an explicit invalidation/build step. Do not fabricate a receipt by hashing an arbitrary already-existing executable: output bytes alone cannot reconstruct R/E/I/A or prove the link recipe.

For recorded executable state, compare the current bounded observation with the **last observed state**, not only with the last successful receipt. Every newly observed change advances E before the next managed Cargo invocation, even when previous invalidations still lack replacement receipts. An identical observed state on a retry does not advance E again. Do not build the archive during this check. A missing tool is an observed missing-input state, not successful validation; it invalidates executable receipts but does not activate LLVM or fail a shared-only build. An actual executable activation will issue the preparation error. See the bounded transitions below.

Cargo then sees changed flags and schedules target compilation/linking normally. This can conservatively rebuild shared/intermediate target units as well as executables: it is not an LLVM runtime choice in those units, but it is extra work. The current common target-rustflags mechanism cannot promise executable-only relinking. No runtime-specific compile macros or LLVM libraries are injected into intermediate code. Precise per-final-unit invalidation would need a separate reviewed Cargo integration, not private fingerprint edits or speculative replay of rustc commands.

Outstanding stale receipts never suppress later changes. Shared-only success never certifies an executable receipt. Invalidation updates only the consumer ledger: it marks applicable receipts stale and records the new observation/E. It must not remove, rename, modify, rebuild or repair producer archives, manifests, indices or generations. Archive corruption remains a producer validation error; even an explicit consumer refresh cannot repair it.

For managed run/test, mandatory receipt/config/output validation must complete before execution. The runner-mediated guard must reject a missing, stale or mismatched receipt **even if Cargo reported the artifact fresh**. It must not build, silently use system unwind, or execute first and warn later. A managed build that claims candidate validation must likewise reject an unverified requested executable at completion. Doctest/direct-execution routes need an equivalent demonstrated pre-execution guard; until covered, they cannot be advertised as guarded candidate execution. This requirement does not change baseline system execution. No stale check is claimed for an unmanaged direct binary launch.

## Bounded consumer state and transitions

Maintain only state for this managed runtime configuration and its executable receipts; this is not a new build scheduler. A stable consumer context C is independent of recipe R, so changing a recipe/profile in that context cannot reset its invalidation history. E is monotonic within C; overflow/corrupt/unreadable state refuses candidate validation rather than wrapping or inventing freshness. Each Cargo invocation uses one immutable (C,R,E) snapshot.

An observation O is the producer validator's bounded description/token of the **observed** declared inputs and cache status: content/inventory changes, missing entries, selection mappings and requested R. It is not verified preparation identity I or proof of unobservable compiler closure. A bare “stale” boolean is insufficient to distinguish successive changes. The producer capability must provide enough bounded observation information; unreadable/indeterminate observations remain unknown and block candidate validation, never equal “unchanged”. There is no claim to detect changes between observations.

Receipt states are **unknown**, **verified for (C,R,E,I,A,output digest)**, and **stale**. A preparation/link may be in flight at a specific R/E, but that is not a verified state. A ledger can retain outstanding stale receipts without calling the entire context a single collapsed “pending change”.

| Observation/action | Consumer transition and failure behavior |
| --- | --- |
| First configuration, no prior observation/receipt | Record static declarations only; no verified identity and no LLVM probes. Existing requested executable without receipt remains unknown. |
| First actual guarded executable link | Prepare lazily; successful final artifact validation may publish its exact output-bound receipt at the invocation's R/E. Failure publishes no verified receipt. |
| Fully observed O equals last observed O; matching receipt and actual output bytes | Retain E; no producer build. Candidate validation also requires the reviewed selected-input/cache checks, not merely this equality. |
| New observed O differs from last observed O, regardless of outstanding stale receipts | Atomically advance E and record O, marking affected receipts stale. The new (R,E) must reach Cargo-visible flags before the next managed Cargo invocation. |
| Identical O repeated after failed preparation/link | Retain the already advanced E; leave receipts stale/unknown. No retry-induced revision churn and no cache repair. |
| Another new change while earlier R/E is building or failed | Advance E again. An old in-flight result cannot certify the newer revision. |
| Input states S0 -> S1 -> S0 in three successive observations | Advance for both S0 -> S1 and S1 -> S0; do not deduplicate against a historical set of previously seen states. An unobserved transient is outside the guarantee. |
| Missing receipt or output digest/length mismatch discovered, including a Cargo-fresh artifact | Mark unknown/stale; record this newly observed artifact state and invalidate once for that distinct observation. Reject required completion/execution. Explicit rebuild must establish provenance; recording a new digest alone cannot certify it. |
| Shared-only build succeeds while executable receipts are stale | Preserve stale executable state; no LLVM preparation and no executable certification. |
| Producer cache bytes/index/manifest invalid | Record invalid observation, invalidate applicable consumer receipts and reject required validation. Leave producer cache byte-for-byte untouched; no repair or deletion. |
| Successful link result for older R/E after a newer observation committed | It cannot replace the current verified receipt or move E backwards. Retain at most bounded historical evidence; reject its use as current. |
| Current successful result | Hash and validate actual final output bytes; bind C/R/E/I/A and producer provenance; publish the receipt atomically only if the invocation snapshot is still current and the required checks pass. |
| Missing/unreadable output, ambiguous observation, malformed ledger/receipt or publication failure | No verified receipt; fail candidate validation/required execution. Never fall back or fabricate identity. |

Serialize each bounded observation plus E-publication transaction within context C, with bounded lock acquisition and validation time. Observe against the current ledger while holding that coordination boundary, then publish before releasing it; a completed distinct observation must not be discarded merely because another build is pending. Do not use a failed compare-and-publish followed by re-observation to silently lose a measured intermediate change. Outside-transaction previews cannot certify freshness. Lock, observation or publication failure leaves the operation uncertified and refuses affected candidate validation; it does not authorize execution or cache repair. Builds use their immutable snapshot and do not hold this coordination lock during LLVM preparation/linking. This coordination is limited to consumer receipt/revision bookkeeping, not a general scheduler.
Required execution validation rehashes the actual output and checks the receipt against the current invocation/context and reviewed input/archive validation. Reusing a pathname, an executable bit, or a Cargo freshness message is insufficient. Post-link modification, a copied artifact without validated context, or a receipt for an older E cannot pass. Concurrency between final validation and execution remains a locally controlled-filesystem boundary; this design is not an adversarial sandbox. No guarantee of unchanged files after validation is invented.

## Plain Cargo and native build-system boundary

Saved shell/TOML plus unmodified plain Cargo has no automatic pre-freshness hook for cargo-libc's external runtime inputs. Therefore this design does NOT promise automatic in-place input-change detection for bare `cargo build/run/test` using an old config.

The required explicit-refresh lifecycle is: validate/invalidate previously activated executable state through the managed preflight/refresh operation, regenerate the configuration to expose its new R/E in Cargo-visible flags, then invoke Cargo. Ordinary config generation alone must not be described as content verification. Recipe/mode/config declaration changes likewise require regeneration; an old config intentionally remains an old selection. The exact refresh interface is undecided and must be reviewed before wiring. Users who need automatic managed checking must enter through the managed command path. No stale-config refusal is claimed when Cargo never starts a helper.

C/CMake/Ninja freshness is a second boundary. libc-cc cannot detect a change if the native build system skips its link command. Cargo's E alone is not proof that a cached build-script CMake tree relinks. Native executable builds need a reviewed propagation of the revision into their actual link command/config dependencies and an exact same-build-directory regression. Direct C/CMake users need the corresponding managed refresh/reconfigure step. No generic support for arbitrary native build systems is implied. Shared C/CMake targets remain system-selected and require no LLVM preparation.

## Required producer capabilities and unresolved scope

- Corrected path handling and independent review before any use.
- Independent libc/header/descriptor provenance roots; contained alias/ordered multiarch header staging without host fallback. Reference-only identity files are not implicit compile include roots. Existing fullsysroot/system behavior remains available.
- A recorded-input validator that can report unchanged/stale/incomplete without compiling or executing LLVM tools, with bounded observation information sufficient to distinguish successive changes and an explicit completeness contract. c7 only exposes prepare(), so this capability is currently absent. If the producer cannot provide it, automatic managed content checking is not yet implementable as described; retain an explicit forced invalidation/refresh boundary rather than pretending recipe identity covers contents.
- Corrected preparation produces actual I/A and a manifest suitable for artifact receipts. Archive integrity failure is never repaired or silently bypassed. Consumer invalidation writes only its own ledger/receipt state, never the producer cache.
- A reviewed executable binding/guard recipe. Hidden U10/U11 failures, native C cleanup/forced-unwind failures, missing personality/helper completeness, foreign-DSO/deep-binding and runtime-loading limits remain blockers. No automatic LLVM default, broad export workaround or process-wide no-libgcc promise is proposed here.

## Acceptance of the lifecycle, not completed evidence

The following are **future required tests, not performed or passing evidence**. Use focused deterministic transition tests and bounded native fixtures, not a general build-system framework:

1. **No-probe/lazy boundary:** system and extension-only configuration generation with LLVM tools unavailable and empty cache; shared/host/rlib/partial outputs never invoke preparation. In a mixed workspace, only guarded actual target-executable links activate the builder.
2. **Revision sequence:** one target directory with verified E0, observed change B -> E1, failed replacement, observed change C -> E2 before any E1 success, then repeated C -> still E2. Verify Cargo receives E1/E2 and actual relinks occur. S0 -> S1 -> S0 observations must produce two advances. Changed recipe/profile participates without resetting the context.
3. **Missing receipt:** force Cargo to report an otherwise fresh requested executable after removing its consumer receipt. Required managed completion/execution must reject, with zero executed fixture markers. Explicit invalidation/build must create a real receipt; no digest-only adoption.
4. **Actual output binding:** replace output bytes at the same path, preserve size/mtime where possible, substitute a different executable, and postprocess a certified output. Each must fail before execution until final bytes are properly recertified. Verify receipts carry output SHA-256/length plus C/R/E/I/A, not only filenames.
5. **Changed selected inputs:** header/resource/tool/libc/archive contents changed at the same paths with preserved mtimes; added/deleted headers and missing inputs. Assert correct new observations/E, producer identities/digests where preparation succeeds, and explicit unknown/refusal where validation cannot complete. No fake all-input guarantee.
6. **Cache separation:** corrupt producer archive/manifest/index; snapshot producer cache before/after consumer invalidation and failed retry, proving no writes/deletion/repair. Legitimate new-input preparation is a separate producer operation, not cache repair.
7. **Bounded failure/concurrency:** failed preparation/link/receipt publication leaves no successful receipt; stale in-flight E1 completion cannot certify E2. Concurrent same-observation checks do not double-advance; distinct newly observed changes do not collapse. Corrupt ledger/ambiguous observations/contention never become fresh. Shared-only success leaves outstanding executable receipts stale.
8. **Execution routes:** managed run/test and each claimed doctest/direct route must demonstrate a pre-execution guard for missing/stale/mismatched receipts even on Cargo-fresh artifacts. Keep unsupported routes explicit; do not claim a universal runner hook.
9. **Saved configuration/native freshness:** both shell and Cargo TOML require explicit refresh/regeneration after changed inputs; inspect changed Cargo-visible revision and actual relink. CMake/Ninja must demonstrate executable relinking in the **same build directory**, with unchanged second-build no-op and shared-only no-preparation control. E alone is not native freshness evidence. Retain current fullsysroot/system controls.

The original hidden-runtime, native C cleanup/forced-unwind, DSO/deep-binding/helper and runtime-loading compatibility blockers remain unchanged. None of these proposed lifecycle tests establishes runtime GO.
